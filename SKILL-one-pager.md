# One-pager: генерация документа по гипотезе

One-pager — короткий документ, по которому принимают решение go / no-go по гипотезе автоматизации. Он отвечает на четыре вопроса: какая проблема, сколько она стоит в часах, что предлагается, что это даст и чего будет стоить.

**Эталонный пример:** `one-pager/one-pager_H-BA-10_confluence-doc-updater.md` — при сомнении в формате раздела смотреть, как он сделан там.

**Формат вывода по умолчанию:** файл Markdown (`.md`).
**Язык:** русский.
**Тон:** деловой, без маркетинга. Утверждения — с источником или пометкой допущения.

---

## Процесс

1. **Собрать вход.** Прочитать всё, что дал пользователь: описание задачи, интервью, переписки, тикеты, расчёты. Данные берутся только оттуда.
2. **Разложить по разделам шаблона.** Каждый факт — в свой раздел. Ничего не выдумывать.
3. **Отметить пробелы.** Всё, чего нет во входных данных, — `[ЗАПОЛНИТЬ: что именно нужно и где взять]`. См. «Правило пробелов».
4. **Посчитать эффект** по формулам ниже, если есть хотя бы одна цифра затрат времени.
5. **Собрать файл** строго по структуре шаблона.
6. **Проверить по чек-листу** в конце скилла.
7. **Отдать файл** пользователю и одной строкой перечислить, что осталось заполнить.

Вопросы пользователю до сборки задавать не нужно — документ собирается сразу, пробелы помечаются. Уточнять стоит только если непонятна сама суть гипотезы.

---

## Правило пробелов

Никогда не подставлять правдоподобные цифры вместо отсутствующих. Вместо этого:

```
[ЗАПОЛНИТЬ: затраты времени респондента, ч/нед — источник: интервью или замер]
```

Пометка всегда говорит **что** нужно и **откуда это взять**. В конце документа собирается раздел «Что нужно уточнить» со всеми пометками списком — чтобы владелец гипотезы видел объём доработки, не перечитывая документ.

Если цифра есть, но она оценочная (не замер), — писать `≈` и в скобках источник оценки: `≈6 ч/мес (экспертная оценка владельца)`.

---

## Расчёт эффекта

Считать явно, показывая арифметику в тексте — читатель должен иметь возможность проверить. Два варианта, выбирать по тому, как приходит боль:

**Вариант А — от месячных затрат** (боль размазана по времени: статусы, отчёты, разбор запросов):

```
T_до     = среднее затрат времени по респондентам, ч/мес
           (часы в неделю × 4,33, если данные недельные)
T_после  = остаточные затраты после внедрения, ч/мес
           (проверка, дозаполнение, разбор ошибок — не ноль)
Эффект   = T_до − T_после, ч/мес
Сокращение = (T_до − T_после) / T_до × 100 %
```

**Вариант Б — от единицы работы** (боль привязана к артефакту: BRD, отчёт, страница):

```
T_до(ед)    = минуты на один артефакт, с разбивкой по этапам
              (напр.: промптинг ≈60 + вычитка ≈100 + перенос ≈20 = 180 мин)
T_после(ед) = то же минус автоматизируемые этапы (остальные этапы не меняются)
Эффект      = (T_до(ед) − T_после(ед)) × частота, артефактов/мес → ч/мес
```

Правила:

- `T_после` никогда не 0. Всегда остаётся контроль результата — это обязательно проговаривается.
- В варианте Б разбивку по этапам показывать всегда: она объясняет, какой именно этап автоматизируется и почему остальные не меняются.
- Показывать состав среднего: `(32 + 28) / 2 = 30 ч/мес — Респондент А 32 ч/мес, Респондент Б 28 ч/мес`.
- Если респондент один — не писать «среднее», писать «по единственному респонденту» и добавить это в риски (низкая репрезентативность).
- Округление: часы — до целых, проценты — до целых, деньги — до целых единиц валюты.
- Экономия в часах — основная метрика. Перевод в деньги делать только если пользователь дал стоимость часа.

**Окупаемость** (если есть и трудозатраты на реализацию, и эффект):

```
Окупаемость (мес) = Затраты на реализацию (ч) / Эффект (ч/мес)
```

## Структура документа

Порядок разделов фиксированный. Разделы 0–8 — обязательные, они есть в каждом one-pager. «Границы решения» и «Что нужно уточнить» — по необходимости (см. их описания).

### Шапка

```markdown
# One pager

# {ID} — {Название гипотезы}
```

Заголовок гипотезы формулируется как действие + объект: «ИИ-агент для публикации и актуализации документов в Confluence». Не «Бот для документов».

Титульная таблица (автор, статус, версия, дата) и оглавление в рабочем Markdown не нужны — они добавляются только при сборке DOCX/PDF для выноса на согласование (см. «Другие форматы»).

### 0. Описание

Самый короткий раздел. ЦА и пользователи — это разные множества, их обязательно разделять.

```markdown
## 0. Описание

- **Owner гипотезы:** {ФИО}
- **ЦА:** {кто выигрывает от решения — нумерованный список групп, каждая с причиной:
  1. новые сотрудники — документация как канал онбординга
  2. разработчики — опираются на документацию при разработке
  …}
- **Кто пользуется агентом:** {кто руками работает с инструментом; на ком пилот и сколько человек}

**Ключевые:**

- Масштабируемо: {Да/Нет} + одно предложение почему {механика не зависит от типа документа / шаблона / роли}
- Критерий успеха: {одна измеримая формулировка — дословно совпадает с первым критерием раздела 8}
- Главный риск: {риск + следствие: «если X — закрываем гипотезу»}
```

### 1. Проблема

Формат — нумерованные утверждения, каждое сразу подкреплено дословной цитатой респондента со ссылкой на транскрипт:

```markdown
## 1. Проблема

1. {Утверждение: кто, на что и как часто тратит время}
> «{дословная цитата}» — {Фамилия И.}, [интервью ДД.ММ.ГГГГ](../Live_interview/{Роль}/{файл}.md)

2. {Следующее утверждение}
> «{цитата}» — {Фамилия И.}, [интервью ДД.ММ.ГГГГ]({ссылка})

**Цена бездействия:**
1. {Юридический / контурный риск — с конкретной нормой, если применимо}
2. {Часы или % времени, которые продолжают тратиться}
3. {Последствия для качества/сроков: ошибки, доработки, задержки релизов}
```

- Цитата — дословная, не пересказ. Ссылка — относительный путь к файлу транскрипта или другому первичному источнику.
- Утверждение без цитаты → `[ЗАПОЛНИТЬ: источник]`.
- Если проблема имеет юридическое измерение (ПДн, банковская тайна) — называть конкретную норму (ст. 26 ФЗ № 395-1, ФЗ № 152-ФЗ, ст. 13.11 КоАП РФ), а не «нарушает требования».
- Боль смежных ролей включать отдельным пунктом — она усиливает масштабируемость из раздела 0.
- Таблица «Респондент | Доказательство | Источник» допустима как компактная альтернатива при 4+ респондентах, но формат «утверждение + цитата» предпочтителен: он читается как аргумент, а не как приложение.

### 2. Решение

Абзац «что это» (класс решения + интерфейс + с чем интегрируется), затем сценарии и три подраздела.

```markdown
## 2. Решение

**{Класс решения, интерфейс}**, который {что делает и с чем работает}.

**Основные сценарии:**
1. **{Название сценария}** — {одно предложение: вход → действие → результат}
2. **{Название}** — {…}
3. **{Массовый / рискованный сценарий}** — {пометить как вторую очередь, согласованно с рисками раздела 5}

### 2.1. Сравнение вариантов архитектур

| | {Вариант А} | {Вариант Б} |
|---|---|---|
| Порог входа | {+/−} | {+/−} |
| Легкость ревью | {+/−} | {+/−} |
| Скорость разработки | {+/−} | {+/−} |
| Удобство UI | {+/−} | {+/−} |

{Абзац-вывод: какой вариант выбран и какой критерий стал решающим.}

### 2.2. Логика работы

{mermaid flowchart TD: от триггера до результата}

### 2.3 Контекст

**Сейчас:**
* {Текущий процесс, тезисно — по одной строке на боль}

**Будет:**
* {Что изменится}
```

Правила раздела:

- **2.1** заполняется, если рассматривались альтернативы (web-интерфейс vs чат-бот и т.п.). Если альтернатив не было — раздел опускается с одной строкой почему.
- **2.2** — mermaid-flowchart (`flowchart TD`), обязательные элементы:
  - ветвление по типу задачи, если сценариев больше одного;
  - показ «было — стало» / превью перед публикацией результата;
  - узел подтверждения человеком с обеими ветками: подтвердил → результат публикуется, не подтвердил → изменение не вносится;
  - если процесс включает ожидание ответа человека — ветка «нет ответа».

Точка человеческого контроля перед публикацией — обязательна. Если её нет во входных данных — поставить `[ЗАПОЛНИТЬ]`, это частая дыра в гипотезах.

### 3. Гипотеза

Одно предложение в формате: **кто** сэкономит **сколько** (часы или %) на **чём**, **если** решение сделает **что** вместо ручного шага.

```markdown
## 3. Гипотеза

{Роль} сэкономит {N ч/мес | N%} времени на {процесс}, если {решение будет делать X вместо человека}.
```

Без числа гипотеза не проверяема — если числа нет, ставится `[ЗАПОЛНИТЬ: ожидаемая экономия]`. Число согласовано с расчётом в разделе 4.

### 4. Эффекты

```markdown
## 4. Эффекты

**Временные:**
- **T_до:** {N} мин на {артефакт} (разбивка по этапам: {этап ≈N + этап ≈N + этап ≈N})
- **T_после:** {N} мин — {какой этап уходит; какие этапы не меняются}
- **Эффект:** ≈{N} мин на {артефакт} (−{N}%). При {частота}/мес это {N} ч/мес на человека

### 4.1 Ценность

* Пользователь перестает:
  * {ручной шаг 1}
  * {ручной шаг 2}
* {Контурная/юридическая ценность, если есть: данные не покидают внутренний контур → снимается риск {норма}}
* {Структурная ценность: качество документации/данных, прозрачность — то, ради чего инициативу поддержат за пределами команды}

### 4.2 Похожий опыт

**{Название/команда}.** {Что делает} (Источник: {Фамилия И.}, [интервью ДД.ММ.ГГГГ]({ссылка}))

**Вывод для нас:** {что из этого следует — чем наш случай отличается или что переиспользуем}
```

- В 4.2 источник обязателен и для внутреннего опыта — имя респондента + ссылка на транскрипт, не «из интервью с коллегой».
- Каждый чужой опыт заканчивается выводом «что из этого следует для нас» — иначе раздел не несёт смысла. Если похожего опыта не нашлось, так и написать: «Похожий опыт не найден» + `[ЗАПОЛНИТЬ: проверить у команд X, Y]`.

### 5. Риски

Таблица с типизацией:

```markdown
## 5. Риски

|№| Риск | Тип | Решение |
|---|---|---|---|
|1| {Риск} | {Тип} | {Как проверяем или снимаем, до какого этапа} |
|2| {…} | {…} | {…} |
```

- **Тип** — один из четырёх: **Поведенческий** (не станут пользоваться), **Данные** (источник неполный/грязный, неверный результат), **Организационный** (доступы, владелец после запуска), **Технический** (интеграция, лимиты API, качество модели). Проверить все четыре категории, включить релевантные.
- Главный риск из раздела 0 обязан присутствовать в таблице.
- Каждый риск идёт в паре с митигацией. Риск без ответа «что с этим делать» — незакрытый вопрос, а не риск.

### 6. Затраты на реализацию

```markdown
## 6. Затраты на реализацию

| Этап | Что входит | Время | Кто нужен |
|---|---|---|---|
| Сбор требований и дизайн сценариев | {…} | {N} дня | {роли} |
| Получение доступов | {API-ключи, согласования} | {N} дня | ИБ-специалист, разработчик |
| Разработка прототипа | {интеграции, LLM, UI} | {N} дней | Разработчик |
| Тестирование работоспособности | {прогон сценариев} | {N} день | Разработчик |
| Пилот | {группа, обучение, сбор обратной связи} | {N} дня | {роль} и {N} пользователей |
| Анализ результатов пилота и решение о запуске | {CustDev, метрики, список доработок} | {N} дня | {роль} |
| Вывод в полноценную эксплуатацию | {правки, промышленные сервера} | {N} дней | Разработчик |
| **Итого** | | **≈{N} рабочих дней** |

Если начать с {дата}, то запуск пилота {дата} и окончание {дата}, а завершение всех этапов — {дата}.
```

- Организационные этапы (доступы, ИБ) — обязательно в таблице, не только разработка.
- «Кто нужен» — роли, не имена.
- **Пилот — календарно реалистичный: обычно 3–4 недели (15–22 рабочих дня), не «5 дней»** — пользователи работают с инструментом в фоне основной работы, метрику использования за неделю не снять.
- Строка «Итого» — жирным, значение равно сумме строк; проверить арифметику.
- Предложение с календарными датами после таблицы — обязательно; даты согласованы с длительностями этапов.
- Эксплуатация (ресурсы/мес) и окупаемость — добавлять строками после таблицы, только если есть данные (стоимость часа, тарифы).

### 7. Шаги по разработке

Нумерованный список; названия шагов 1:1 совпадают с этапами таблицы раздела 6, подзадачи — вложенными пунктами.

```markdown
## 7. Шаги по разработке

1. Сбор требований и дизайн сценариев
2. Получение доступов
3. Разработка прототипа
    * {Интеграция}
    * {Подключение LLM}
    * {UI}
4. Тестирование работоспособности функционала
    * {Прогон кейсов по сценариям}
    * {Проверка отката, конфликта версий}
5. Пилот, {N} пользователя
6. Анализ результатов пилота и принятие решения о запуске
7. Вывод в полноценную эксплуатацию
```

Решение о запуске — отдельный шаг перед выводом в эксплуатацию: one-pager описывает проверку гипотезы, а не гарантированное внедрение.

### 8. Принятие решения о запуске

Измеримые критерии, по которым по итогам пилота принимается решение о масштабировании:

```markdown
## 8. Принятие решения о запуске

Решение о масштабировании принимается по итогам пилота на основе критериев:
* Регулярность использования: {порог — дословно тот же, что «критерий успеха» в разделе 0}
* Качество ответа ИИ: > {N}% принятых от сгенерированных {правок/результатов} на этапе сравнения «было — стало»
* Стабильность работы: отсутствие критических ошибок {перечислить каких: затирание данных, публикация не туда}

**Критерий остановки:** {при каких показателях гипотезу закрываем — порог из «главного риска» раздела 0}
```

Критерий остановки формулируется всегда — гипотеза, которую нельзя опровергнуть, не гипотеза.

### 9. Границы решения (опционально)

Добавлять, когда есть риск расползания объёма на согласовании.

```markdown
## 9. Границы решения

**Входит в объём:**
- {…}

**Не входит в объём:**
- {Что сознательно оставляем за рамками и почему}

**Зависимости:**
- {Доступы, интеграции, данные, люди, без которых работа не начнётся — с владельцем}
```

### 10. Что нужно уточнить (только при пробелах)

```markdown
## 10. Что нужно уточнить

- [ ] {Пробел из документа} — у кого спросить: {роль}
- [ ] {…}
```

Сюда собираются все `[ЗАПОЛНИТЬ]` из документа. Если пробелов нет — раздел не создаётся.

## Правила оформления

- Даты в тексте — `ДД.ММ.ГГГГ`.
- Оценочные величины — со знаком `≈`.
- Единицы: `ч/нед`, `ч/мес`, `мин`, `дней`. Перевод недель в месяцы — коэффициент 4,33.
- Проценты — целые, со знаком `%`.
- Заголовки — по шаблону, нумерация разделов не меняется (по ней ссылаются на согласовании).
- Таблицы — строго с шапкой; пустая ячейка — `—`, а не пробел.
- Ссылки на транскрипты и внутренние файлы — относительные пути от файла one-pager (`../Live_interview/…`), в формате `[текст](url)`, не голым URL.
- Mermaid — валидный синтаксис `flowchart TD`; проверить, что диаграмма рендерится.
- Никаких эмодзи.
- Имена в примерах шаблона — плейсхолдеры, в готовом документе их быть не должно.

## Чек-лист перед выдачей

Пройти по списку и исправить, а не просто отметить.

1. Все разделы 0–8 присутствуют и в правильном порядке.
2. В разделе 0 разделены ЦА (кто выигрывает) и пользователи (кто работает с инструментом).
3. В разделе 1 каждое утверждение подкреплено дословной цитатой со ссылкой на источник; юридические утверждения — с конкретной нормой.
4. Гипотеза (раздел 3) содержит число (часы или %) и слово «если»; число согласовано с разделом 4.
5. `T_после` не равно нулю; разбивка T_до по этапам показана; арифметика сходится (сумма этапов = T_до; эффект × частота = ч/мес).
6. В mermaid-диаграмме есть превью «было — стало» и узел подтверждения человеком с обеими ветками.
7. У каждого риска — тип и митигация; проверены 4 категории; главный риск из раздела 0 есть в таблице раздела 5.
8. Сумма строк таблицы затрат равна «Итого»; календарные даты согласованы с длительностями; пилот измеряется неделями, не днями.
9. Названия шагов раздела 7 совпадают с этапами таблицы раздела 6.
10. Критерий успеха из раздела 0 дословно совпадает с первым критерием раздела 8; в разделе 8 есть критерий остановки.
11. Все пробелы помечены `[ЗАПОЛНИТЬ: …]` и продублированы в разделе 10 (если пробелы есть).
12. Нет утверждений без источника или пометки «оценка»; плейсхолдеров вида `{…}` из шаблона не осталось.

## Другие форматы

По умолчанию — Markdown. Если пользователь просит иной формат, содержание не меняется, меняется только сборка:

- **DOCX** — читать SKILL.md скилла `docx`; добавить титульную страницу (автор, статус, версия, дата в формате «7 сентября, 2026»), автособираемое оглавление, колонтитул с названием подразделения и гипотезы, нумерацию страниц.
- **PDF** — читать SKILL.md скилла `pdf`; титул и оглавление — как для DOCX.

Оба формата собираются из готового Markdown, а не пишутся заново.
