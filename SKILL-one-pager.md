# One-pager: генерация документа по гипотезе

One-pager — короткий документ, по которому принимают решение go / no-go по гипотезе автоматизации. Он отвечает на четыре вопроса: какая проблема, сколько она стоит в часах, что предлагается, что это даст и чего будет стоить.

**Формат вывода по умолчанию:** файл Markdown (`.md`).
**Язык:** русский.
**Тон:** деловой, без маркетинга. Утверждения — с источником или пометкой допущения.

---

## Процесс

1. **Собрать вход.** Прочитать всё, что дал пользователь: описание задачи, интервью, переписки, тикеты, расчёты. Данные берутся только оттуда.
2. **Разложить по разделам шаблона.** Каждый факт — в свой раздел. Ничего не выдумывать.
3. **Отметить пробелы.** Всё, чего нет во входных данных, — `[ЗАПОЛНИТЬ: что именно нужно и где взять]`. См. «Правило пробелов».
4. **Посчитать эффект** по формулам ниже, если есть хотя бы одна цифра затрат времени.
5. **Собрать файл** строго по структуре шаблона.
6. **Проверить по чек-листу** в конце скилла.
7. **Отдать файл** пользователю и одной строкой перечислить, что осталось заполнить.

Вопросы пользователю до сборки задавать не нужно — документ собирается сразу, пробелы помечаются. Уточнять стоит только если непонятна сама суть гипотезы.

---

## Правило пробелов

Никогда не подставлять правдоподобные цифры вместо отсутствующих. Вместо этого:

```
[ЗАПОЛНИТЬ: затраты времени респондента, ч/нед — источник: интервью или замер]
```

Пометка всегда говорит **что** нужно и **откуда это взять**. В конце документа собирается раздел «Что нужно уточнить» со всеми пометками списком — чтобы владелец гипотезы видел объём доработки, не перечитывая документ.

Если цифра есть, но она оценочная (не замер), — писать `≈` и в скобках источник оценки: `≈6 ч/мес (экспертная оценка владельца)`.

---

## Расчёт эффекта

Считать явно, показывая арифметику в тексте — читатель должен иметь возможность проверить.

```
T_до     = среднее затрат времени по респондентам, ч/мес
           (часы в неделю × 4,33, если данные недельные)
T_после  = остаточные затраты после внедрения, ч/мес
           (проверка, дозаполнение, разбор ошибок — не ноль)
Эффект   = T_до − T_после, ч/мес
Сокращение = (T_до − T_после) / T_до × 100 %
```

Правила:

- `T_после` никогда не 0. Всегда остаётся контроль результата — это обязательно проговаривается.
- Показывать состав среднего: `(32 + 28) / 2 = 30 ч/мес — Респондент А 32 ч/мес, Респондент Б 28 ч/мес`.
- Если респондент один — не писать «среднее», писать «по единственному респонденту» и добавить это в риски (низкая репрезентативность).
- Округление: часы — до целых, проценты — до целых, деньги — до целых единиц валюты.
- Экономия в часах — основная метрика. Перевод в деньги делать только если пользователь дал стоимость часа.

**Окупаемость** (если есть и трудозатраты на реализацию, и эффект):

```
Окупаемость (мес) = Затраты на реализацию (ч) / Эффект (ч/мес)
```

## Структура документа

Порядок разделов фиксированный. Разделы 0–7 — обязательные, они есть в каждом one-pager. Разделы 8–10 добавляются по умолчанию и убираются только если пользователь просит краткую версию.

### Шапка и оглавление

```markdown
# One pager

**{Подразделение или команда}**
{Дата в формате «7 сентября, 2026»}

| | |
|---|---|
| **Идентификатор** | {ID гипотезы, напр. XX-19, или [ЗАПОЛНИТЬ]} |
| **Название** | {Короткое название гипотезы} |
| **Автор документа** | {Кто пишет} |
| **Статус** | Черновик / На согласовании / Утверждён |
| **Версия** | v1 |
| **Обновлён** | {ДД.ММ.ГГГГ} |

# {ID} — {Название гипотезы}
```

Заголовок гипотезы формулируется как действие + объект: «Автосбор и оформление еженедельного отчёта по задачам команды». Не «Бот для отчётов».

### 0. Описание

Кто владелец, для кого, и три ключевых ответа. Самый короткий раздел — до 10 строк.

```markdown
## 0. Описание

- **Инициатор / owner гипотезы:** {ФИО}
- **Целевая аудитория:** {кто конкретно страдает от проблемы и будет пользоваться решением}

**Ключевые:**

- Является ли продукт повторяемым и масштабируемым? {Да/Нет + одно предложение почему}
- Ключевой критерий успеха: {одна измеримая формулировка}
- Риски: {главный риск одной строкой, подробности — в разделе 5}
```

### 1. Проблема

Проблема измеряется в часах и подтверждается источниками. Без таблицы раздел не считается заполненным.

```markdown
## 1. Проблема

{1–3 предложения: кто, на что и как часто тратит время. Без слова «решение».}

| Респондент | Затраты времени | Источник |
|---|---|---|
| {Фамилия И.} | ≈{N} ч/мес ({X} ч/нед × 4,33) | Интервью {ДД.ММ.ГГГГ} |
| {Фамилия И.} | ≈{N} ч/мес ({X} ч/нед × 4,33) | {Сообщение в чате / замер / тикет} |

{1–2 предложения: что будет, если не автоматизировать — цена бездействия.}
```

Источник обязателен для каждой строки. Строка без источника — это `[ЗАПОЛНИТЬ: источник цифры]`.

### 2. Решение

Сначала абзац «что это», потом пронумерованная логика работы — по шагам, от триггера до результата.

```markdown
## 2. Решение

{Абзац: что делает решение, с чем интегрируется, где заканчивается его ответственность
и где начинается человеческая проверка.}

**Логика работы:**

1. {Триггер — что запускает процесс}
2. {Действие}
3. {Ветвление, если есть: а) … б) …}
4. {Что происходит при отсутствии ответа / ошибке}
5. {Формирование результата}
6. {Проверка человеком перед публикацией}

### 2.1 Контекст

**Как сейчас:**

- {Текущий процесс, по шагам или тезисно}

**Как будет:**

- {Что изменится — отдельно для каждой роли: заказчик, исполнитель, руководитель}
```

В логике работы обязательно должны быть: обработка отсутствия ответа, и точка человеческого контроля перед публикацией результата. Если их нет во входных данных — поставить `[ЗАПОЛНИТЬ]`, это частая дыра в гипотезах.

### 3. Гипотеза

Одно предложение в формате: **кто** сэкономит **сколько** на **чём**, **если** сделать **что**.

```markdown
## 3. Гипотеза

{Роль} сэкономит ≈{N} часов в месяц на {процесс}, если {решение будет делать X вместо человека}.
```

Без числа гипотеза не проверяема — если числа нет, ставится `[ЗАПОЛНИТЬ: ожидаемая экономия, ч/мес]`.

### 4. Эффекты

```markdown
## 4. Эффекты

### Выгоды

- **T_до:** {формула среднего} = {N} ч/мес — {разбивка по респондентам}
- **T_после:** {N} ч/мес — {на что уходит остаток: проверка, дозаполнение}
- **Эффект (экономия):** ≈{N} ч/мес (≈{N}% сокращения)

### 4.1 Ценность

{Пользовательская ценность: что человек перестаёт делать руками.}

**Структурная ценность:**
{Что решение даёт процессу в целом — качество данных, соблюдение регламента,
прозрачность. Это то, ради чего инициативу поддержат за пределами одной команды.}

### 4.2 Похожий опыт

{Команда или продукт с похожей задачей, ссылка.}

**Была ли зафиксирована экономия времени?**
{Ответ}

**Какой функционал оказался самым востребованным на практике?**
{Ответ}

**С какими проблемами столкнулись?**
{Ответ}

- {Как это применимо или неприменимо к нашему случаю}
```

В 4.2 каждый чужой опыт заканчивается выводом «что из этого следует для нас» — иначе раздел не несёт смысла. Если похожего опыта не нашлось, так и написать: «Похожий опыт не найден» + `[ЗАПОЛНИТЬ: проверить у команд X, Y]`.

### 5. Риски

```markdown
## 5. Риски

**Потенциальные риски:**

- {Риск} — **решение:** {как проверяем или снимаем, до какого этапа}
- {Риск} — **решение:** {…}
```

Каждый риск идёт в паре с митигацией. Риск без ответа «что с этим делать» — незакрытый вопрос, а не риск.

Обязательно проверить наличие четырёх типовых рисков и включить релевантные:

- **Поведенческий** — люди не станут отвечать/пользоваться;
- **Данные** — источник неполный, грязный, недоступен;
- **Организационный** — не согласуют доступы, нет владельца после запуска;
- **Технический** — лимиты API, качество модели, нагрузка.

### 6. Затраты на реализацию

```markdown
## 6. Затраты на реализацию

| Этап | Время |
|---|---|
| {Получение доступов} | {N} дней |
| {Согласование входных данных} | {N} дня |
| {Разработка} | {N} дней |
| {Тестирование} | {N} день |
| **Итого** | **≈{N} дней** |

**Эксплуатация:** {объём использования в месяц}, {ресурсы: запросы, токены, лицензии},
стоимость ≈{N} в месяц.

**Окупаемость:** {затраты, ч} / {эффект, ч/мес} = ≈{N} мес.
```

В таблицу обязательно включать организационные этапы (доступы, согласования), а не только разработку — они обычно составляют большую часть срока. Строка «Итого» — жирным, значение должно совпадать с суммой строк; проверить арифметику.

### 7. Шаги по разработке

Последовательность работ от изучения процесса до решения о запуске. Нумерованный список, вложенность — для подзадач.

```markdown
## 7. Шаги по разработке

1. Изучение текущих процессов
2. Сбор требований
3. Получение доступов
4. Согласование входных данных
5. Разработка
   1. {Интеграции}
   2. {Сценарии}
6. Тестирование
   1. Проверка работоспособности
   2. Проверка сценариев
7. Анализ результатов
8. Принятие решения о запуске
```

Последним шагом всегда идёт решение о запуске — one-pager описывает проверку гипотезы, а не гарантированное внедрение.

### 8. Границы решения

Раздел, которого чаще всего не хватает: он защищает от расползания объёма на согласовании.

```markdown
## 8. Границы решения

**Входит в объём:**

- {…}

**Не входит в объём:**

- {Что сознательно оставляем за рамками и почему}

**Зависимости:**

- {Доступы, интеграции, данные, люди, без которых работа не начнётся — с владельцем}
```

### 9. Как измеряем результат

```markdown
## 9. Как измеряем результат

| Метрика | До | Цель | Как замеряем | Когда |
|---|---|---|---|---|
| {Затраты времени, ч/мес} | {N} | ≤{N} | {Способ замера} | Через {N} недель после запуска |
| {Доля обработанных без ручной правки} | — | ≥{N}% | {Способ} | Еженедельно |

**Критерий успеха пилота:** {что должно быть верно, чтобы признать гипотезу подтверждённой}
**Критерий остановки:** {при каких показателях сворачиваем}
```

Критерий остановки формулируется всегда — гипотеза, которую нельзя опровергнуть, не гипотеза.

### 10. Что нужно уточнить

```markdown
## 10. Что нужно уточнить

- [ ] {Пробел из документа} — у кого спросить: {роль}
- [ ] {…}
```

Сюда собираются все `[ЗАПОЛНИТЬ]` из документа. Если пробелов нет — раздел удаляется.

## Правила оформления

- Даты в тексте — `ДД.ММ.ГГГГ`; дата на титуле — `7 сентября, 2026`.
- Оценочные величины — со знаком `≈`.
- Единицы: `ч/нед`, `ч/мес`, `дней`. Перевод недель в месяцы — коэффициент 4,33.
- Проценты — целые, со знаком `%`.
- Заголовки — по шаблону, нумерация разделов не меняется (по ней ссылаются на согласовании).
- Таблицы — строго с шапкой; пустая ячейка — `—`, а не пробел.
- Никаких эмодзи.
- Имена в примерах шаблона — плейсхолдеры, в готовом документе их быть не должно.
- Ссылки — в формате `[текст](url)`, не голым URL.

## Имя файла

```
one-pager_{ID}_{короткое-название-транслитом}_{ГГГГ-ММ-ДД}.md
```

Пример: `one-pager_DL-19_weekly-report-autocollect_2026-09-07.md`

## Чек-лист перед выдачей

Пройти по списку и исправить, а не просто отметить.

1. Все разделы 0–7 присутствуют и в правильном порядке.
2. В разделе 1 есть таблица, и у каждой строки указан источник.
3. Гипотеза (раздел 3) содержит число и слово «если».
4. `T_после` не равно нулю, арифметика в разделе 4 сходится, процент пересчитан.
5. Экономия в разделе 4 соответствует числу в гипотезе (раздел 3).
6. В логике работы есть обработка отсутствия ответа и точка человеческой проверки.
7. У каждого риска есть митигация; проверены 4 типовых категории риска.
8. Сумма строк таблицы затрат равна «Итого».
9. Проверены остальные внутренние противоречия: сроки в разделе 6 не расходятся с шагами в разделе 7.
10. Все пробелы помечены `[ЗАПОЛНИТЬ: …]` и продублированы в разделе 10.
11. Нет утверждений без источника или пометки «оценка».
12. Плейсхолдеров вида `{…}` из шаблона в файле не осталось.

После выдачи файла — одна строка пользователю: сколько пунктов осталось заполнить и какие из них блокируют согласование.

## Другие форматы

По умолчанию — Markdown. Если пользователь просит иной формат, содержание не меняется, меняется только сборка:

- **DOCX** — читать SKILL.md скилла `docx`; титульная страница, автособираемое оглавление, колонтитул с названием подразделения и гипотезы, нумерация страниц.
- **PDF** — читать SKILL.md скилла `pdf`.

Оба формата собираются из готового Markdown, а не пишутся заново.
